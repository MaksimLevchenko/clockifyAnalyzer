# Редактирование сохранённых элементов через модалки — требования

Статус: реализовано и проверено 2026-08-13. Реализационно влияющих неизвестных нет.

## 1. Executive Summary

- **Problem Statement:** сохранённые пользователем элементы во многих списках либо нельзя изменить,
  либо они меняются разными способами прямо в строке. Удаление также расположено и подтверждается
  непоследовательно.
- **Proposed Solution:** оставить в каждой строке только постоянный карандаш, открывающий модалку со
  всеми изменяемыми полями элемента, сохранением и удалением. Удаление сохранённого элемента всегда
  требует отдельного подтверждения.
- **Success Criteria:**
  - 100% перечисленных сохраняемых элементов открываются по карандашу.
  - В строках перечисленных списков нет полей, остановки или удаления вне модалки.
  - Все сохраняемые параметры элемента доступны в его редакторе.
  - Каждое удаление сохранённого элемента требует подтверждения.
  - Сохранение, остановка и удаление немедленно пересчитывают все зависимые представления.

## 2. User Experience & Functionality

### User Personas

Единственный пользователь приложения «Денежный горизонт», который ведёт личную историю дохода,
расходов, баланса и рабочих записей.

### User Stories

- Как пользователь, я хочу нажать карандаш у сохранённого элемента и изменить его параметры, чтобы
  не удалять и не создавать запись заново.
- Как пользователь, я хочу остановить повторяющееся правило расхода в той же модалке, чтобы прошлые
  списания сохранились.
- Как пользователь, я хочу удалить элемент из модалки с подтверждением, чтобы случайно не изменить
  прошлые и будущие расчёты.
- Как пользователь, я хочу редактировать базовую версию дохода через её карточку, чтобы отдельные
  поля настройки не дублировали модель.

### Acceptance Criteria

- Карандаш присутствует у рабочей записи, правила расхода, разового поступления, отпуска, записи
  баланса, версии дохода, базового дня зарплаты и фактической даты выплаты.
- В настройках базовой почасовой версии нет отдельных полей ставки, веса истории и налога; они
  редактируются по карандашу базовой карточки версии дохода.
- Валюта остаётся общей настройкой, потому что не является версией дохода.
- Базовые дни зарплаты остаются отдельным списком по решению пользователя; каждый день меняется в
  собственной модалке.
- У небазовой версии дохода можно изменить дату начала, тип дохода, соответствующую метрику, налог,
  вес истории и правила выплат.
- Базовая версия остаётся почасовой и не удаляется; в её модалке меняются ставка, налог и вес истории.
- Для правила расхода доступны вид, название, сумма или процент, денежная база процента, дата/день,
  период действия и годовой рост там, где они применимы.
- Повторяющееся правило расхода можно остановить с выбранной даты в модалке; прошлое влияние
  сохраняется. Удаление правила исключает его влияние из прошлого и будущего.
- Для разового поступления доступны название, сумма и дата.
- Для отпуска доступны название, начало и окончание.
- Для записи баланса доступны дата, сумма и вид «факт/цель».
- Для фактической выплаты доступны дата прихода и необязательная дата учёта часов.
- Строка ожидающей выплаты в настройках редактируется через карандаш; из модалки можно изменить дату
  учёта, завершить ожидание датой выплаты либо удалить ожидание.
- Существующая рабочая запись сохраняет нынешнюю модалку; её удаление получает обязательное
  подтверждение.
- Удаление небазовой версии дохода сохраняет прежнюю семантику: предыдущая версия действует до
  следующего перехода.
- Ошибки дат, дублей, диапазонов и обязательных значений показываются до изменения состояния.
- Закрытие модалки крестиком, Escape или отменой не меняет состояние.
- Карандаш имеет доступное имя и видимый фокус; модалка переводит фокус в первое поле.

### Non-Goals

- Перенос форм добавления в модалки.
- Изменение формата экспортируемого состояния или добавление идентификаторов существующим массивам.
- Редактирование вычисленных интервалов фактического cash-flow как пользовательских записей.
- Перенос быстрых действий «Учесть часы» и «Указать выплату» с главной страницы.
- Визуальный редизайн приложения за пределами существующих токенов и стиля диалогов.

### Story Map

Backbone: **Найти элемент → Открыть редактор → Изменить → Сохранить или удалить → Проверить пересчёт**.

#### Release 1 — walking skeleton

- У каждой перечисленной строки есть карандаш и нет прямых полей/удаления.
- Один каркас модалки обслуживает открытие, отмену, сохранение и удаление.
- Все типы элементов имеют собственные поля и валидацию.
- Удаление подтверждается, изменения сразу сохраняются и пересчитываются.
- Базовые поля версии дохода перенесены в модалку её карточки.

#### Release 2 — deferred

- Перенос форм добавления в тот же каркас модалки.
- Дополнительные клавиатурные ускорители.

#### Release 3 — deferred

- Массовое редактирование и массовое удаление.
- Отмена последнего изменения.

## 4. Technical Specifications

### Architecture Overview

- Общий edit-dialog module владеет жизненным циклом диалога, фокусом, отменой, сохранением,
  видимостью удаления и подтверждением удаления.
- `js/app.js` сохраняет владение расходами, поступлениями, отпусками, балансом и рабочими записями;
  формы редакторов плановых элементов выносятся из большого файла в сфокусированный UI module.
- `js/income-model-ui.js` владеет редактором версий дохода.
- `js/payday-ui.js` владеет редакторами базовых дней зарплаты, фактических дат и ожидания выплаты.
- Существующие функции `saveState`, рендеры и расчётное ядро остаются единственным путём применения
  изменений; отдельная копия бизнес-правил не создаётся.

### Integration Points

- `localStorage` и существующая Gist-синхронизация получают тот же объект состояния.
- Экспорт и импорт продолжают работать без миграции схемы.
- Сервер, API и авторизация отсутствуют.

### Security & Privacy

- Новых внешних передач данных нет.
- Пользовательские значения вставляются в разметку только через существующее экранирование.
- Подтверждение удаления называет тип удаляемого элемента и необратимое влияние на расчёты.

## 5. Risks & Roadmap

### Phased Rollout

- **MVP:** весь подтверждённый Release 1 одним изменением, чтобы не оставлять смешанное поведение.
- **v1.1:** формы добавления в модалках только по отдельному запросу.
- **v2.0:** массовые операции и undo только по отдельному запросу.

### Technical Risks

- `saveState()` синхронизирует базовую версию из legacy-полей; редактор базы обязан сначала менять
  `state.rate`, `state.halfLife` и `state.taxRate`, иначе сохранённые значения будут перезаписаны.
- Отсортированные списки нельзя безопасно редактировать по отображаемому индексу без обратного
  поиска исходной записи; редакторы используют исходный объект либо стабильный ключ существующей
  модели.
- Изменение даты записи баланса или версии дохода может создать дубликат; сохранение блокируется до
  разрешения конфликта.
- Прямое редактирование правил расхода затрагивает прошлый расчёт; модалка должна ясно отличать
  остановку от полного удаления.

## Вопросы и ответы

1. Какие элементы охватить? Все созданные пользователем элементы списков, которые сейчас нельзя
   полноценно изменить.
2. Где расположить удаление? Внутри модалки.
3. Что делать с отдельными полями базовой модели? Убрать; оставить карандаш карточки и модалку.
4. Где редактировать дни выплат базы? В отдельном списке, каждый через собственный карандаш.
5. Нужно ли подтверждение удаления? Да, всегда для сохранённых элементов.

## Architecture review gate

Дата: 2026-08-13.

Временный HTML-отчёт создан и открыт; локальный путь намеренно не сохраняется в репозиторной
документации.

Область проверки: `index.html`, `styles.css`, `js/app.js`, `js/income-model-ui.js`,
`js/payday-ui.js`, `js/state.js` и эта спецификация.

Кандидаты:

- Общий edit-dialog module — **Strong, принят**. Он создаёт один interface для жизненного цикла,
  доступности и подтверждения удаления, обеспечивая locality и одинаковое поведение всех редакторов.
- Новые стабильные идентификаторы для всех массивов — **Speculative, отклонён**. Модалки применяют
  изменения синхронно, а существующие объекты/ключи достаточны; миграция не даёт нужного leverage.
- Одновременный перенос форм добавления — **Speculative, отложен** как отдельный пользовательский
  поток вне подтверждённого объёма.

Итог: **Recommendation should change the spec**. Принятый общий module и распределение предметных
редакторов отражены в Architecture Overview и подробной спецификации. Реализация может начинаться
только после команды пользователя `implement`.

# Незавершённый учёт часов до фактической выплаты — спецификация

Источник требований: [pending-accrual-requirements.md](./pending-accrual-requirements.md).

Статус: принята для архитектурной проверки; реализация не начата.

# Часть 1. Человекочитаемое описание

## 1. Проблема и контекст

Дата закрытия часов известна раньше даты фактической выплаты. Сейчас приложение требует обе даты
одновременно и не позволяет честно отразить деньги, которые уже рассчитаны, но ещё неизвестно когда
придут.

## 2. Поведение для пользователя

- В блоке исключений можно нажать «Учесть часы сегодня» либо выбрать день учёта вручную.
- После этого появляется одна заметная запись «Ждёт выплаты».
- Пока день выплаты не указан, часы считаются закрытыми по выбранную дату, заработок остаётся
  невыплаченным и не увеличивает баланс.
- Когда деньги приходят, пользователь может указать дату в этой записи либо добавить фактическую
  выплату обычным способом. В обоих случаях приложение связывает выплату с ожидающим днём учёта.
- После связи запись становится обычным завершённым исключением из расписания.

## 3. Цели

- Разделить момент фиксации часов и момент, когда становится известна выплата.
- Не завышать прогнозный баланс неизвестным поступлением.
- Сохранить однозначную связь одной незавершённой отсечки со следующей фактической выплатой.

## 4. Не-цели

- Несколько незавершённых отсечек.
- Ручной ввод суммы выплаты.
- Автоматический выбор плановой даты вместо неизвестной фактической.
- Изменение расписания зарплаты.

## 5. UX-поток

1. Пользователь выбирает дату учёта либо нажимает «Учесть часы сегодня».
2. Приложение сохраняет одну незавершённую запись и показывает сумму/часы в статусе ожидания.
3. Добавление второго незавершённого дня блокируется.
4. После прихода денег пользователь указывает выплату в строке ожидания или добавляет её в форме.
5. Приложение создаёт завершённую пару дат и очищает ожидание.

## 6. Человеческие критерии приёмки

- После фиксации часов без выплаты баланс не растёт ни в прошлом, ни в прогнозе.
- Сумма и часы отображаются как ожидающие выплаты без выдуманной даты прихода.
- Следующая введённая выплата использует сохранённую границу часов.
- Нельзя незаметно потерять или задвоить незавершённую отсечку.

# Часть 2. Спецификация реализации для AI-агента

## 8. Функциональные требования

- F1. Добавить `state.pendingPayAccrual: string|null`.
- F2. Валидная незавершённая дата имеет формат `YYYY-MM-DD` и не позже `today()`.
- F3. Одновременно существует не более одной незавершённой даты.
- F4. Незавершённая дата закрывает период `(предыдущая accrual, pendingPayAccrual]`.
- F5. У закрытого периода нет денежного поступления, пока payout неизвестен.
- F6. При вводе выплаты создать `{payout, accrual: pendingPayAccrual}` в `payDayActuals` и очистить
  `pendingPayAccrual`.
- F7. Автосвязь F6 работает и через строку ожидания, и через общую форму добавления выплаты.
- F8. Если ожидания нет, существующий поток добавления исключения работает без изменений.
- F9. Удаление ожидания вновь открывает часы после последней завершённой отсечки.

## 9. Бизнес-правила

- B1. «Учтены часы» и «деньги поступили» — независимые факты.
- B2. Неизвестная выплата никогда не заменяется плановой датой.
- B3. Ожидающий заработок входит в показатели невыплаченного, но не в баланс.
- B4. Следующая фактическая выплата закрывает единственную ожидающую отсечку.
- B5. Дата выплаты не может быть раньше ожидающей даты учёта.

## 10. Изменения модели данных

- В `migrate(s)` нормализовать `pendingPayAccrual` в валидную дату либо `null`.
- Не помещать незавершённую запись в `payDayActuals`.
- Экспорт/импорт и Gist уже переносят неизвестные поля общего объекта состояния; отдельная схема
  транспорта не требуется.
- Старые состояния получают `null`; существующие `payDayActuals` не меняются.

## 11. API и сервер

Изменений нет.

## 12. Изменения ядра

- Представить незавершённую отсечку в расчётной модели как событие `{accrual, payout:null}`.
- Сортировка периодов выполняется по `accrual`; сортировка денежных событий игнорирует `payout:null`.
- `payPeriodEarned` рассчитывает сумму ожидающего периода обычным правилом периода.
- `forecastSavings`:
  - закрывает открытый пул в `pendingPayAccrual`;
  - хранит полученный лот до конца горизонта без даты освобождения;
  - включает его в `initialUnpaid`, `unpaidNow`, `pendingNow` и `unpaidAtEnd`;
  - не включает в `payDayDates` и `nextSalary`;
  - возвращает `pendingNow.nextPayout = null`.
- `cashFlowFromCheckpoints` не считает ожидающий период выплаченным.
- `reconstructPastBalance` не создаёт ступень дохода для ожидающего периода.

## 13. Изменения клиента

- Передать `pendingPayAccrual` во все расчётные вызовы через `opts`.
- Переставить поля формы: сначала «Учтены часы по», затем необязательный «День выплаты».
- Добавить кнопку «Учесть часы сегодня».
- Разрешить добавление только дня учёта.
- При активном ожидании отключить создание второго ожидания и показать строку со статусом,
  датой, рассчитанными часами/суммой, вводом выплаты и удалением.
- При добавлении выплаты через общую форму автоматически использовать ожидающую дату учёта.
- В сводке для `nextPayout:null` показывать «дата выплаты пока не указана».
- На графике показывать маркер учёта; маркер выплаты отсутствует до закрытия.

## 14. Состояние и операции

- Операции создания, завершения и удаления ожидания должны поддерживать инвариант «не более одной».
- Завершение проверяет формат дат, порядок `accrual <= payout` и отсутствие дубля payout.
- После каждой операции сохраняются состояние и зависимые представления пересчитываются один раз.

## 15. Разрешения

Не применимо.

## 16. Краевые случаи

- Пустое расписание: существующее ограничение сохраняется — фактические исключения недоступны.
- Дата учёта в будущем отклоняется.
- Выплата раньше даты учёта отклоняется.
- Дубликат даты выплаты отклоняется.
- Удаление ожидания не создаёт завершённого события.
- Импорт состояния с невалидным `pendingPayAccrual` даёт `null`.
- Если ожидающая дата совпадает с завершённой accrual, миграция сохраняет завершённое событие и
  очищает конфликтующее ожидание.

## 17. Ошибки, загрузка и пустые состояния

- Без ожидания показывается существующая подсказка об отсутствии исключений.
- При ожидании дата выплаты явно обозначена как неизвестная.
- Ошибки валидации показываются через существующий `toast`.
- Асинхронных состояний загрузки нет.

## 18. Валидация

- Формат даты: `YYYY-MM-DD`.
- `pendingPayAccrual <= today()`.
- Дату с уже завершённой явной accrual нельзя открыть повторно.
- При завершении: `pendingPayAccrual <= payout`.
- Уникальность payout среди `payDayActuals`.

## 19. План тестирования

В репозитории нет тестовой инфраструктуры. До production-кода подготовить точечный Node-сценарий,
который проверяет:

- нормализацию нового поля;
- период с `payout:null`;
- отсутствие поступления в прогнозе;
- включение суммы в ожидающие и невыплаченные показатели;
- отсутствие ожидающей суммы в cash-flow и реконструкции;
- превращение ожидания в `{payout, accrual}`;
- регрессию существующих завершённых событий.

После реализации выполнить `node --check` для всех JS-файлов и ручную проверку пользовательского
потока в браузере.

## 20. Миграция и выкатка

- Миграция выполняется при загрузке состояния.
- Новый клиент сохраняет отдельное поле в JSON/Gist.
- Старый клиент не использует поле, но не должен удалять его при обычном сохранении общего объекта.
- Зависимостей и серверной миграции нет.

## 21. Критерии приёмки реализации

- AC1. Все критерии человекочитаемой части воспроизводятся в браузере.
- AC2. Ожидающий период не увеличивает баланс ни в одном расчётном пути.
- AC3. Ожидающий период входит в невыплаченный заработок и остаётся им на конце горизонта.
- AC4. Оба способа завершения создают одну одинаковую завершённую пару.
- AC5. Старые состояния и существующие завершённые события работают без изменения.
- AC6. Синтаксические проверки JS проходят.

документации.

Проверены модули выплат и прогноза в `js/core.js`, миграция в `js/state.js`, два UI-пути в
`js/app.js`, события/сводка прогноза и форма в `index.html`.

Аудит кандидатов:

- Новый pay-ledger module — **Speculative**, отклонён: удаление модуля лишь вернёт ту же сложность
  в `core.js`; отдельного adapter нет, а новый interface не увеличит leverage текущих проверок.
- State-operation helpers — **Speculative**, отклонены: при двух местах вызова они будут shallow.

Итог: **No architecture change recommended**.

Принято:

- `pendingPayAccrual` остаётся отдельным полем состояния;
- `payout:null` остаётся внутренним представлением незавершённого события;
- одна локальная функция завершения в `app.js` обслуживает редактирование строки и общую форму;
- существующий pay-event implementation в `core.js` сохраняет владение расчётными правилами.

Обновлённые разделы: §14 уточнён единым владением операцией завершения; финальный план ниже
зафиксирован по итогам проверки. Остальные разделы уже покрывали рекомендацию.

### Post-implementation architecture review

Strict maintainability review выявил структурную регрессию: реализация увеличивала `js/app.js` до
1099 строк. Принят **Strong**-кандидат на отдельный `js/payday-ui.js`.

- `js/payday-ui.js` (148 строк) владеет расписанием, формой исключений, ожиданием и обоими путями
  завершения.
- Его внешний interface: `renderPayDays` и `renderPayDayActuals`.
- `js/app.js` уменьшен до 953 строк и сохраняет общую оркестрацию.
- `js/core.js` сохраняет расчётную модель; правила не дублируются в UI.

Временный post-implementation HTML-отчёт создан и открыт 2026-07-27; локальный путь не сохраняется
в репозиторной документации. Итог: **Architecture accepted**.

### Architecture review gate для главной

Проверены `index.html`, `styles.css`, `js/payday-ui.js`, `js/app.js` и существующий file input
`#file-merge`.

Кандидаты:

- **Strong, принят:** расширить существующий payday UI module новым представлением
  `renderHomePayday()`, сохранив единые операции начала/завершения/удаления. Это даёт locality
  бизнес-правил и leverage для двух экранов.
- **Speculative, отклонён:** создать отдельный home-payday module. У него был бы один adapter и
  широкий interface к операциям payday, а реализация была бы shallow.
- **Отклонён:** второй file input для догрузки. Кнопка на главной программно открывает
  существующий `#file-merge`, поэтому новый input и обработчик только увеличат поверхность ошибок.

Итог: **Recommendation should change the spec** — дополнение выше фиксирует расширение interface
`js/payday-ui.js` и переиспользование `#file-merge`. Временный HTML-отчёт создан и открыт
2026-07-27; локальный путь не сохраняется в документации.

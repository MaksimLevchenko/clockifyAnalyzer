# Отметка фактического дня зарплаты — интервью требований

Статус: интервью завершено (спецификация ещё не пишется — ждём команду «напиши спеку»).

## Контекст задачи

Зарплата иногда приходит на пару дней раньше или позже запланированного дня. Сейчас
«дни выплаты» (`state.payDays`) заданы только как **числа месяца 1–28**, и модель считает,
что зп приходит строго в эти числа каждого месяца. Нужна возможность **отметить
фактическую дату** прихода зп, чтобы расчёты учитывали реальный сдвиг.

### Найденные паттерны

- `state.payDays` — массив чисел 1–28 (максимум 4); пустой → доход начисляется ежедневно (старое поведение).
- Сумма зарплаты **нигде не хранится** — вычисляется из часов × ставка (минус налог).
  «День выплаты» = момент, когда накопленный заработок попадает на баланс.
- Единственная точка, где число месяца превращается в дату — `lastPayDayBefore`. Её результат
  потребляют: `cashFlowFromCheckpoints` (границы прошлых периодов) и `forecast initialUnpaidWork`
  (стартовый пул) — обе работают с **прошлыми** датами (чекпоинты ≤ сегодня).
- Будущие дни выплаты в прогнозе берутся из `paySet`/`isPay(ds)` — это **числа месяца**, спроецированные
  на будущее. Фактические даты (прошлое) в будущий диапазон прогноза не попадают.
- Данные — `localStorage`, миграция в [state.js](../../../../js/state.js). Тестовой инфраструктуры в репозитории нет.

### Подтверждено из кода

- Чтобы учесть сдвиг зп в расчётах, достаточно обобщить `lastPayDayBefore`, чтобы для конкретной
  запланированной выплаты он возвращал её фактическую дату (если отмечена).
- Будущая часть прогноза (`isPay`/`paySet`) трогать не нужно — фактические даты только прошлые.

## Вопросы и ответы

1. **Как отмечать фактический день зп?**
   Почему важно: определяет формат данных и логику сопоставления.
   Ответ: **«Просто фактическая дата»** — добавляешь конкретную дату прихода зп; приложение само
   сопоставляет её с ближайшим запланированным днём выплаты (в пределах ~недели) и в расчётах
   использует фактическую дату вместо запланированной. Если расписание не задано — дата считается
   самостоятельной выплатой.

2. **На что должны влиять отмеченные даты?**
   Почему важно: определяет, трогаем ли будущую часть прогноза.
   Ответ: **«Только прошлое»** — cash-flow между чекпоинтами и стартовый «невыплаченный» пул прогноза.
   Будущие выплаты в прогнозе остаются по расписанию (числа месяца).

3. **Что сохранять при отметке?**
   Почему важно: наличие суммы меняет модель данных и возможную калибровку.
   Ответ: **«Только дату»** — сумма зп по-прежнему вычисляется из часов × ставка.

## Подтверждённые решения

- Новое поле состояния: список **фактических дат выплат** (полные `YYYY-MM-DD`), отдельно от
  `state.payDays` (числа месяца). Сумма не хранится.
- Фактическая дата **подменяет** ближайшую запланированную выплату в том же окне (а не добавляется
  второй выплатой) — иначе граница периода задвоится.
- Сопоставление детерминированное: фактическая дата заменяет запланированную выплату с минимальным
  расстоянием в днях.
- Влияние — **только на прошлое**: `cashFlowFromCheckpoints`, стартовый пул прогноза
  (`initialUnpaidWork`/`initPool`) **и сама симуляция прогноза**. Диапазон прогноза начинается с
  якорного чекпоинта, поэтому он включает прошлые дни (якорь→сегодня); в этом отрезке выплата
  «прилетает» на **фактическую** дату, а не на запланированную. Будущие выплаты (после сегодня)
  остаются строго по расписанию — фактических дат там нет.
- Реализационно: `isPay(ds)` в прогнозе сверяется с множеством **эффективных дат выплат**
  (`effectivePayDays`), где прошлые запланированные дни заменены отмеченными фактическими; будущие —
  по расписанию. Это держит тайминг зарплаты в симуляции согласованным со стартовым пулом.
- UI — внутри карточки «Дни выплаты»: подраздел для добавления/удаления фактических дат
  (ввод даты + список), даты в будущем не принимаются (область = только прошлое). Подраздел
  активен только при заданном расписании (см. D2).

### Правило границы периода (R1)

- **Граница периода — фактическая дата выплаты**, а не запланированная. Часы, отработанные
  **строго после** фактической выплаты, относятся к **новому** (ещё не выплаченному) периоду.
  Часы в день выплаты закрываются этой же выплатой (старый период).
- Пример (ранняя зп): факт 4-го, ожидалось 6-го → работа 5-го относится к новому периоду
  (`5 > 4`), несмотря на «расписание» 6-го.
- Пример (поздняя зп): факт 8-го, ожидалось 6-го → работа 7-го попадает в период, закрываемый
  выплатой 8-го (`7 ≤ 8`); работа 9-го — новый период.
- Реализационно: уже существующая логика накопления (`e.date > граница` в
  [core.js:680](../../../../js/core.js#L680), `since = граница+1` в
  [core.js:328](../../../../js/core.js#L328)) корректна — достаточно, чтобы `lastPayDayBefore`
  возвращал **фактическую** дату подменённой выплаты вместо запланированной.

## Дефолты (приняты, не требуют отдельного вопроса)

- **D1 (окно сопоставления).** Фактическая дата сопоставляется с запланированной выплатой,
  если расстояние ≤ **7 дней**; при нескольких кандидатах берётся ближайший по модулю дней.
  За пределами окна дата трактуется как самостоятельная выплата (вставляется, а не подменяет).
- **D2 (расписание обязательно для фактических дат).** Фактические даты имеют смысл только как
  корректировка существующего расписания, поэтому **без заданных `payDays` отметить фактическую дату
  нельзя**: в UI поле даты и кнопка «Отметить» заблокированы и показывается подсказка. В расчётах
  (`cashFlowFromCheckpoints`, прогноз) фактические даты применяются только при непустом расписании;
  без расписания доход начисляется ежедневно (как раньше), а фактические даты игнорируются —
  на случай импортированного/устаревшего состояния. Будущие выплаты в прогнозе всегда по расписанию.
- **D3 (валидация).** Принимаются только корректные даты ≤ сегодня; дубли дат игнорируются;
  список хранится отсортированным по возрастанию.
- **D4 (предупреждение).** Предупреждение «дни выплаты не настроены» ([app.js](../../../../js/app.js))
  показывается, когда расписание пусто (доход начисляется ежедневно), независимо от фактических дат.

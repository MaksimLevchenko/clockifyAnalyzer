# Разделение «дня зп» и «дня выплаты» — интервью требований

Статус: интервью завершено. Реализационно влияющих неизвестных нет (кроме деталей,
помеченных как «решается в спецификации»). Следующий шаг — по команде «напиши спеку».

## Контекст задачи

Сейчас один параметр `state.payDays` (числа месяца) обозначает **и** отсечку начисления, **и**
момент поступления денег на баланс. Пользователь хочет развести два понятия:

- **День зп** — отсечка часов: какая работа попала в эту зарплату.
- **День выплаты** — когда деньги реально пришли на карту (рост баланса).

**Пример пользователя.** День зп — 1-е, день выплаты — 5-е. 5-го приходят деньги за работу
**до 1-го числа** включительно; работа **2–5** уходит уже в **следующую** зарплату.

> Прямое указание пользователя: «Это должно учитываться в прогнозе, не забывай».

Связанная фича: [фактические даты выплат](../actual-dates/actual-dates-requirements.md).

### Найденные паттерны

- `state.payDays` — массив чисел 1–28 (макс 4); пустой → доход начисляется ежедневно (старое поведение).
- Сумма зарплаты не хранится — считается из часов × ставка (минус налог).
- Фактические даты (`payDayActuals`) подменяют ближайшую запланированную выплату (≤7 дн.).

### Подтверждено из кода

- Разделение требует пары значений на каждое событие выплаты и «отложенного пула» в симуляции.
- Граница периода для часов (день зп) и момент роста баланса (день выплаты) становятся разными датами.

## Вопросы и ответы

1. **Как привязать день выплаты к дням зп (их до 4)?**
   Ответ: **своя пара у каждого** — у каждого дня зп своё необязательное поле «день выплаты».

2. **Чем станут существующие значения `payDays`?**
   Ответ: **днём зп** (день учёта/отсечки часов). Новое поле «день выплаты» по умолчанию = день зп.

3. **К чему относится «фактическая дата выплаты»?**
   Ответ: **к реальному приходу денег** (фактический день выплаты). Отсечка часов (день зп)
   остаётся по расписанию.

4. **Применять разделение к прошлому или только к будущему?**
   Ответ: **везде одинаково** — прогноз, реконструкция прошлого, cash-flow, авто-расход.

## Подтверждённые решения

- **Модель.** На каждый день зп (число месяца) — необязательный **день выплаты** (число месяца).
  Не задан → день выплаты = день зп (текущее поведение, обратная совместимость).
- **Семантика.** Часы/период определяются **днём зп**: работа `> предыдущего дня зп` и `≤ дня зп`
  попадает в эту зарплату. Деньги зачисляются на баланс в **день выплаты**.
  Пример (1-е/5-е): отсечка 1-го, деньги 5-го; работа 2–5 — следующий период.
- **Кросс-месяц.** Если число дня выплаты `<` числа дня зп — выплата уходит в **следующий** месяц
  (отсечка 28-го, выплата 3-го → 3-е следующего месяца). Если `≥` — тот же месяц.
- **Фактические даты.** `payDayActuals` = фактический **день выплаты** (приход денег). Отсечка
  часов (день зп) — по расписанию, фактические даты её не двигают.
- **Область.** Разделение действует **везде**: симуляция прогноза (отложенный пул), стартовый пул,
  `prevSalary`/`nextSalary`/`unpaidNow`, `cashFlowFromCheckpoints`, `reconstructPastBalance`,
  авто-расход.
  - Деньги в прогнозе/прошлом появляются на балансе в день выплаты; «ожидаемая/предыдущая зарплата»
    датируется днём выплаты, а её часы — периодом дня зп.
- **Миграция.** Существующие `state.payDays` → дни зп; день выплаты не задан (= день зп).

## Дефолты (приняты, не требуют отдельного вопроса)

- **D1.** Пустой список дней зп → доход начисляется ежедневно (как сейчас), дни выплаты не применяются.
- **D2.** День выплаты валиден так же, как день зп: 1–28.
- **D3.** Кросс-месяц определяется автоматически по сравнению чисел (см. «Подтверждённые решения»),
  отдельного флага «след. месяц» не вводим.
- **D4.** Фактические даты по-прежнему требуют заданного расписания дней зп (как в actual-dates).

## Остающиеся неизвестные (решаются в спецификации)

- **Форма хранения и миграция.** Вариант A: `payDays` (числа дня зп) + параллельный `payoutDays`
  (выровненный массив, `null` = совпадает с днём зп). Вариант B: массив объектов
  `[{accrual, payout}]`. Выбрать на этапе спецификации (с учётом синка/экспорта состояния).
- **Новое промежуточное состояние «начислено, ждёт выплаты».** Между днём зп и днём выплаты сумма
  уже отсечена, но ещё не на карте. Нужно ли показывать отдельной карточкой в блоке
  «Зарплата и невыплаченное» (например, «Начислено, ждёт выплаты N · придёт DD») — решить в спеке
  (предложение: показывать, т.к. это прямое следствие разделения).
- **Перекрытие пулов.** При нескольких днях зп с разными сдвигами возможно несколько одновременно
  «ждущих выплаты» пулов — модель симуляции должна вести их раздельно (деталь реализации).
- **UI карточки «Дни выплаты».** Переименование/подписи (день зп + день выплаты на строку),
  обновление хинтов — финализируется в спеке.

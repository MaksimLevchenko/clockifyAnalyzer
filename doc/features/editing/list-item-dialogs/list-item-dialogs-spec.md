# Редактирование сохранённых элементов через модалки — спецификация

Источник требований: [list-item-dialogs-requirements.md](./list-item-dialogs-requirements.md).

Статус: реализовано и проверено 2026-08-13.

## 1. Поведение для пользователя

Каждая сохранённая строка показывает данные как текст и одну операцию — карандаш. Карандаш открывает
модалку с полным набором применимых полей. «Сохранить изменения» валидирует черновик, одним действием
обновляет состояние и закрывает модалку. «Удалить» находится там же и перед применением показывает
подтверждение. Отмена никогда не меняет состояние.

## 2. Охват

| Элемент | Поля редактора | Особые правила |
| --- | --- | --- |
| Рабочая запись | дата, проект, часы, ставка, описание | сохранить существующую модалку; добавить подтверждение удаления |
| Правило расхода | вид, название, сумма/процент, база процента, дата/день, начало, рост | остановка повторяющегося правила доступна в модалке; удаление убирает всю историю |
| Разовое поступление | название, сумма, дата | дата обязательна |
| Отпуск | название, начало, окончание | начало не позже окончания |
| Запись баланса | дата, сумма, факт/цель | дата уникальна |
| Версия дохода | начало, тип, ставка/оклад, налог, вес истории, выплаты | база не удаляется и остаётся почасовой; остальные версии полностью редактируются |
| Базовый день зарплаты | день 1–28 | отдельный список, максимум четыре уникальных дня |
| Фактическая выплата | день прихода, необязательная граница часов | приход уникален; граница не позже прихода |
| Ожидание выплаты | граница часов, необязательный день прихода | день прихода завершает ожидание; удаление подтверждается |

Вычисленные cash-flow интервалы, формы добавления и быстрые действия главной не входят в охват.

## 3. UX и доступность

- Использовать существующий символ карандаша `✎` и класс иконки; добавить `aria-label` и `title` с
  названием типа элемента.
- Карандаш видим постоянно, а не только при наведении, поэтому доступен на сенсорных устройствах.
- Один общий `<dialog>` содержит заголовок, динамическую форму, сообщение валидации и действия.
- Порядок действий: слева destructive «Удалить», справа «Отмена» и primary «Сохранить изменения».
- Для неудаляемой базовой версии кнопка удаления отсутствует.
- Подтверждение удаления выполняется отдельным системным confirm с предметным текстом.
- При открытии фокус получает первое изменяемое поле; после закрытия фокус возвращается карандашу.
- Escape, крестик и «Отмена» закрывают диалог без сохранения.
- На мобильном поля складываются в одну колонку в рамках существующих breakpoints.
- Новые цвета, шрифты и декоративные паттерны не вводятся.

## 4. Общий edit-dialog module

Добавить `js/edit-dialog.js` перед предметными UI-скриптами.

Его внешний interface:

- `openEditDialog(config)` — открывает диалог с заголовком, разметкой полей, начальным фокусом,
  функцией чтения/валидации черновика и callbacks сохранения/удаления.
- `closeEditDialog()` — закрывает без применения и возвращает фокус источнику.

Module скрывает:

- единственный активный редактор;
- обработку submit, Escape, крестика и отмены;
- показ ошибки валидации;
- видимость destructive-действия;
- обязательный confirm перед callback удаления;
- защиту от двойного submit.

Предметные callbacks получают уже проверенный черновик и выполняют существующие мутации/рендеры.
HTML предметных полей и бизнес-валидация не переносятся в общий module.

## 5. Плановые элементы

Добавить сфокусированный `js/plan-item-editors.js`, чтобы не увеличивать `js/app.js`. Его interface —
`openPlanItemEditor(kind, locator, trigger)`, где `kind` — expense, income, vacation или checkpoint.

- `locator` для записи баланса — исходная дата; для остальных — ссылка на исходный объект или его
  индекс в несортированном массиве.
- Сохранять копию значений в полях; объект состояния не мутируется до успешного submit.
- После сохранения/удаления вызывать тот же набор рендеров и расчётов, что текущие прямые обработчики.
- Для записи баланса после изменения даты вызвать `pruneStaleExclusions()`.
- Для расхода условно показывать применимые поля по виду и способу задания суммы.
- «Остановить с» для повторяющегося расхода записывает `endDate = stopDate - 1 день`; очистка
  остановки возвращает правило в активное состояние. Остановка не считается удалением.

`renderExpenses`, `renderIncomes`, `renderVacations` и `renderCheckpoints` выводят только текстовые
значения и карандаш; существующие inline inputs, stop/delete buttons и listeners удаляются.

## 6. Версии дохода

`js/income-model-ui.js` получает editor draft, независимый от draft формы добавления.

- Базовая карточка получает карандаш.
- Базовый редактор содержит ставку, вес истории и налог; тип, дата начала и выплаты не меняются.
- Перед `saveState()` базовый редактор записывает значения одновременно в legacy-поля
  `state.rate`, `state.halfLife`, `state.taxRate`; `syncLegacyIncomeModel()` остаётся совместимым.
- Валюта переносится в небольшую карточку общих настроек и продолжает использовать существующее поле
  `in-currency`.
- Небазовый редактор позволяет изменить `effectiveFrom`, тип, метрику, вес истории, налог и до
  четырёх правил выплат.
- При смене типа неприменимые значения нормализуются теми же правилами, что при создании перехода.
- Дата начала небазовой версии уникальна; после сохранения вызывается `normalizeIncomeModels`.
- Удаление доступно только небазовой версии и сохраняет прежнюю семантику временной шкалы.
- В строке карточки нет отдельной кнопки удаления.

## 7. Выплаты

`js/payday-ui.js` открывает общий диалог для трёх видов записей.

- Базовый день: изменение проверяет диапазон 1–28 и уникальность; удаление сохраняет ограничение
  активного `pendingPayAccrual` для последнего дня.
- Фактическая выплата: editor использует исходный объект из `state.payDayActuals`, а не индекс
  отсортированного представления.
- Ожидание: редактор позволяет изменить `pendingPayAccrual`; заполненный payout использует
  существующую операцию завершения. Удаление вызывает существующую очистку после confirm.
- Прямые date inputs и delete buttons из `pd-list`/`pda-list` удаляются; кнопки добавления и быстрые
  действия остаются.

## 8. Сохранение и удаление

- Успешный submit изменяет состояние один раз, вызывает `saveState()` один раз и затем общий набор
  зависимых рендеров.
- Валидационная ошибка не закрывает диалог и не меняет состояние.
- Confirm удаления выполняется до мутации; отказ оставляет модалку и черновик открытыми.
- Тексты подтверждения различают остановку правила и удаление всей истории.
- После удаления модалка закрывается, список и прогноз обновляются.

## 9. Модель данных и миграция

Новых полей состояния и миграции нет. Существующие JSON, импорт, экспорт и Gist-синхронизация
сохраняют совместимость. Новые стабильные идентификаторы не добавляются.

## 10. Валидация и краевые случаи

- Все суммы и проценты конечны и удовлетворяют текущим диапазонам.
- Даты обязательны там же, где при создании соответствующего элемента.
- Дубли дней зарплаты, дат выплат, дат баланса и дат начала версий блокируются.
- Нельзя сохранить конец отпуска раньше начала.
- Нельзя остановить расход не позже даты его начала.
- Нельзя сохранить выплату раньше границы учёта часов.
- При внешнем обновлении состояния открытая модалка не применяет устаревший locator: элемент повторно
  разрешается перед сохранением, иначе показывается «Запись больше не существует».
- Вложенное удаление правила выплаты из черновика версии применяется только после общего сохранения;
  отмена возвращает исходную версию.

## 11. Проверка

Автоматической тестовой инфраструктуры нет, поэтому новые тесты без отдельного запроса не создаются.
После реализации выполнить:

1. `node --check` для всех изменённых JavaScript-файлов.
2. Ручной smoke-check каждого типа редактора: открыть, отменить, сохранить, удалить/отказаться от
   удаления, проверить список.
3. Регрессию расчёта после правки расхода, записи баланса и обеих типов версии дохода.
4. Импорт пользовательского состояния и проверку, что существующие элементы открываются без миграции.
5. Клавиатурную проверку Tab, Shift+Tab, Escape и возврата фокуса.

## 12. Architecture review gate

- **Strong, принят:** общий `js/edit-dialog.js` для жизненного цикла и удаления.

  редакторы извлекаются из `js/app.js` в `js/plan-item-editors.js`.
- **Speculative, отклонён:** миграция всех записей на новые id.

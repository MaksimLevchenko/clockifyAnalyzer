# Разделение «дня зп» и «дня выплаты» — спецификация

Источник требований: [accrual-payout-split-requirements.md](./accrual-payout-split-requirements.md).
Статус: реализовано.

> **Уточнение по ходу реализации (по запросу пользователя).** Финальный дизайн упрощён: в
> расписании остаётся **только «день зп»** (число месяца; день прихода денег по умолчанию тот же —
> отдельного фиксированного «дня выплаты» в расписании НЕТ, поле `state.payoutDays` не используется).
> Варьирование дня прихода по месяцам задаётся через **«Фактические даты выплат»**, где каждая запись
> теперь пара `{payout, accrual}` — фактический день прихода денег + фактический день учёта часов
> (`accrual` опц., null = по дню зп). Соответственно `effectivePayEvents` по умолчанию даёт события
> `payout==accrual`, а пары-актуалы переопределяют событие месяца. Разделы 11/13.9 ниже описывают
> исходный вариант (с `payoutDays` в расписании) и оставлены как история решения.

# ЧАСТЬ 1. Человекочитаемое описание

## 1. Проблема / контекст

Сейчас один параметр «Дни выплаты» обозначает сразу две вещи: и **момент отсечки** (какая работа
попала в зарплату), и **момент поступления** денег на карту. В реальности это часто разные даты:
зарплата считается по работе до одного числа, а деньги приходят на несколько дней позже.

## 2. Поведение для пользователя

- В карточке выплат у каждой строки теперь **два** числа месяца:
  - **День зп** — до какого числа учитываются часы (отсечка периода).
  - **День выплаты** — когда деньги реально приходят на карту. Поле **необязательное**: если пусто,
    выплата считается в тот же день, что и день зп (как сейчас).
- Часы и сумма зарплаты определяются **днём зп**; деньги появляются на балансе в **день выплаты**.
- Пример: день зп — 1-е, день выплаты — 5-е. 5-го на карту приходят деньги за работу **по 1-е
  включительно**; работа **со 2-го по 5-е** уходит уже в следующую зарплату.
- Если день выплаты по числу меньше дня зп (напр. отсечка 28-го, выплата 3-го) — выплата приходит в
  **следующем месяце**.
- «Фактические даты выплат» (ранняя/поздняя зп) теперь означают **реальный день прихода денег**;
  отсечка часов остаётся по расписанию.
- Всё это учитывается **одинаково** и в прогнозе вперёд, и в реконструкции прошлого, и в расчёте
  фактического оттока (cash-flow / авто-расход).
- В блоке «Зарплата и невыплаченное» появляется состояние **«Начислено, ждёт выплаты»** — деньги,
  которые уже отсечены (день зп прошёл), но ещё не пришли на карту (день выплаты не наступил).

## 3. Цели

- Точно моделировать задержку между начислением и поступлением зарплаты.
- Сохранить обратную совместимость: у кого день выплаты не задан — поведение не меняется.

## 4. Не-цели

- Не хранить фактическую сумму зарплаты (по-прежнему считается из часов × ставка − налог).
- Не вводить «сдвиг в днях»: только числа месяца (день зп / день выплаты).
- Не менять модель будущих выплат на «по факту» (фактические даты — только прошлое, как и раньше).

## 5. UX-поток

1. На вкладке «Данные» → «Дни выплаты»: для каждой строки два поля — «День зп» и «День выплаты»
   (плейсхолдер «= день зп»).
2. Пользователь задаёт, например, день зп 1, день выплаты 5.
3. Прогноз и сводка сразу пересчитываются: деньги в графике появляются 5-го, часы периода — по 1-е.
4. Блок «Зарплата и невыплаченное» показывает прошлую/ожидаемую выплату по **дню выплаты**, а также
   «ждёт выплаты», если сейчас между отсечкой и поступлением.

## 6. Человеческие критерии приёмки

- Задал день зп 1, день выплаты 5 → на графике прогноза рост баланса от зарплаты приходится на 5-е,
  а не на 1-е.
- Работа 2–5 числа не входит в выплату 5-го (она за период по 1-е).
- Пустой день выплаты → всё как раньше (поступление = день зп).
- «Ожидаемая зарплата» датируется днём выплаты в будущем; «Предыдущая зарплата» — последним днём
  выплаты ≤ сегодня.

# ЧАСТЬ 2. Спецификация реализации (для AI-агента)

## 9. Функциональные требования

- F1. Каждая запись расписания = пара `{accrual, payout}` (числа месяца 1–28), `payout` опционален
  (`null` ⇒ `= accrual`).
- F2. Период зарплаты, закрываемый отсечкой `A` (день зп), охватывает работу `(A_prev, A]`, где
  `A_prev` — предыдущая отсечка по всему расписанию.
- F3. Деньги этого периода зачисляются на баланс в дату выплаты `P(A)`.
- F4. `P(A)`: то же число месяца `payout` в месяце отсечки, если `payout ≥ accrual`; иначе — в
  следующем месяце.
- F5. Фактические даты (`payDayActuals`) переопределяют ближайшую запланированную **дату выплаты**
  (окно ≤ 7 дн.); отсечка не двигается.
- F6. Модель применяется в: `forecastSavings`, реконструкции прошлого, `cashFlowFromCheckpoints`,
  авто-расходе, `prevSalary`/`nextSalary`/`unpaidNow`.
- F7. Пустое расписание (`payDays` пуст) ⇒ ежедневное начисление (без изменений).

## 10. Бизнес-правила

- B1. Отсечка определяет **часы и сумму** периода; выплата — **момент роста баланса**.
- B2. Между отсечкой и выплатой сумма периода находится в состоянии «ждёт выплаты» (на балансе её ещё нет).
- B3. Несколько периодов могут одновременно «ждать выплаты» (если новая отсечка наступила раньше
  выплаты предыдущей) — вести раздельно.
- B4. Кросс-месяц по правилу F4, без отдельного флага.

## 11. Изменения модели данных (Вариант A — обратносовместимый)

`js/state.js`:

- `state.payDays: number[]` — **остаётся** массивом чисел = дни **зп** (отсечка). Без изменения формы.
- `state.payoutDays: (number|null)[]` — **новое**, выровнено по индексу с `payDays`; `payoutDays[i]`
  = день выплаты для `payDays[i]`; `null`/отсутствует ⇒ `= payDays[i]`.
- Миграция в `migrate(s)`:
  - `payDays` — как сейчас (числа 1–28, ≤4, отсортированы по возрастанию, дедуп).
  - `payoutDays`: привести к массиву длины `payDays.length`; каждый элемент — `null` либо число 1–28;
    лишние/недостающие — обрезать/добить `null`; если поля нет → массив `null`-ов.
  - **Важно:** сортировка/дедуп `payDays` должны переставлять `payoutDays` синхронно. Реализовать
    через построение пар `{accrual, payout}`, сортировку/дедуп пар по `accrual`, обратную разборку в
    два массива.
- Причина выбора Варианта A: старые клиенты (через gist) проигнорируют `payoutDays` и продолжат
  использовать `payDays` как дни выплаты (грациозная деградация к текущему поведению).

## 12. API/сервер

Изменений нет (статическое приложение).

## 13/14. Изменения ядра (`js/core.js`) и состояния

### 13.1. Хелперы расписания

```
function paySchedule(payDays, payoutDays){
  // -> [{accrual:int, payout:int}] отсортировано по accrual, payout = payoutDays[i] ?? accrual,
  //    оба клампятся в 1..28. Возвращает [] для пустого payDays.
}
```

### 13.2. События выплат (замена effectivePayDays)

```
function effectivePayEvents(start, end, schedule, actuals){
  // schedule: [{accrual, payout}]
  // 1. Спроецировать на месяцы в [start-40д, end+40д]:
  //    для каждого месяца (Y,M) и записи: accrualDate=Y-M-accrual;
  //    payoutDate = (payout>=accrual) ? Y-M-payout : (следующий месяц)-payout.
  // 2. Отсортировать события по payout (затем accrual).
  // 3. Применить actuals: каждая фактическая дата (по возр.) занимает ближайшее несвязанное
  //    событие с |event.payout - actual| <= PAYDAY_MATCH_WINDOW(7) -> event.payout = actual.
  //    Несвязанные actuals -> standalone {accrual:actual, payout:actual}.
  // 4. Вернуть события, у которых accrual∈[start,end] ИЛИ payout∈[start,end] (consumer фильтрует).
  // Возврат: [{accrual:'YYYY-MM-DD', payout:'YYYY-MM-DD'}] отсортировано по payout.
}
```

- Существующую `effectivePayDays` можно сохранить как тонкую обёртку (вернуть `.map(e=>e.payout)`),
  если где-то нужны только даты поступления, либо удалить после рефактора всех вызовов.

### 13.3. Период и заработок по событию

```
function periodEarned(es, accrualDate, prevAccrualDate, fallbackRate){
  // сумма по es: date > prevAccrualDate (или с начала, если null) и date <= accrualDate
  // -> {gross, hours}.  (Налог применяет вызывающий.)
}
```

`prevAccrualDate` — accrual предыдущего события (по сортировке accrual). Для самого раннего — `null`.

### 13.4. Состояние «на момент refDate»

Заменяет `initialUnpaidWork` для нового пула:

```
function payoutStateAt(es, refDate, schedule, actuals, fallbackRate, taxRate){
  // Возвращает:
  //  openMoney/openHours  — заработок (lastAccrual<=ref, ref] (net) — текущий незакрытый период
  //  pending: [{payout:'YYYY-MM-DD', money, hours}]  — события c accrual<=ref и payout>ref
  //           (закрыто, но ещё не на карте); money уже net.
  //  lastPayout / prevPeriod — для prevSalary (см. 13.6)
}
```

- `lastAccrual<=ref`: последняя accrualDate ≤ ref среди спроецированных событий (если нет — период с
  начала данных).

### 13.5. Симуляция (`forecastSavings`)

Сигнатура: добавить параметр `payoutDays` (или принимать готовый `schedule` через `opts`). Внутри:

- `useDelayed = schedule.length>0`.
- Построить события `effectivePayEvents(start, end, schedule, payDayActuals)`.
  - `accrualToPayout: Map(accrualDate -> payoutDate)` для accrual∈[start,end].
  - Множество `payoutInRange` для payout∈[start,end].
- Сиды (на anchor): `st = payoutStateAt(es, balanceDate, schedule, payDayActuals, rate, taxRate)`.
  - `openPool[s] = st.openMoney` (net), `openHours0 = st.openHours`.
  - Начальные «ждущие» лоты: для каждого `st.pending` создать лот `{payout, amount:Float64Array(nSims).fill(money), hours}` (детерминированная сумма из реальных данных).
- В цикле по дням:
  - Накопление: `openPool[s] += work(s)`; параллельно детерминированно `openExpH += grossExpH`.
  - Если `ds` — accrualDate (∈ accrualToPayout): закрыть период — создать лот
    `{payout: accrualToPayout[ds], amount: copy(openPool), hours: openExpH}`; `openPool[s]=0`,
    `openExpH=0`.
  - Если `ds` — payout одного/нескольких лотов (`lot.payout==ds`): для каждого такого лота
    `run[s] += lot.amount[s]` (+ зафиксировать `payDayDates.push(ds)`), удалить лот. Это **момент
    роста баланса от зарплаты**.
  - Не-delayed ветка (`!useDelayed`) — без изменений (ежедневное начисление).
- `unpaidAtEnd` = среднее (openPool + сумма оставшихся лотов) на конец.
- `payDayDates` теперь = **даты выплат** (для тиков на графике и счётчика «выплат в периоде»).

### 13.6. prevSalary / nextSalary / unpaidNow (в `forecastSavings`)

- `prevSalary` (последняя выплата ≤ ref): среди событий найти max payout ≤ ref; сумма = `periodEarned`
  его периода (net); `date = payout`; `hours`; `periodFrom = prevAccrual+1`, `periodTo = accrual`.
- `nextSalary` (первая выплата ≥ ref в горизонте): из симуляции — лот, выплачиваемый в эту дату;
  `mean/p10/p90` по `lot.amount`; `date = payout`; `expHours = lot.hours`.
  - Захват: первый `payout` день с `ds>=ref`, у которого высвобождается лот.
- `unpaidNow` / `unpaidNowHours` = `st.openMoney + Σ st.pending.money` / соответств. часы
  (всё, что ещё не на карте на сегодня).
- **Новое поле** `pendingNow = { money: Σ st.pending.money, hours: Σ st.pending.hours,
  nextPayout: min(st.pending.payout) }` — для карточки «Начислено, ждёт выплаты».

### 13.7. cashFlowFromCheckpoints

- «Выплачено в (A,B]» = Σ по событиям с `payout∈(A,B]` от `periodEarned` их периода (net).
  Заменяет текущую логику `earnFrom/earnTo` через `lastPayDayBefore`.
- Остальное (delta, implicit, устойчивые оценки) — без изменений по форме.
- Принимает `payoutDays`/`schedule` дополнительно.

### 13.8. reconstructPastBalance

- При наличии расписания: дневной `known(d)` = (если `d` — дата выплаты: сумма `periodEarned`
  закрытого периода net) + (разовые поступления в `d`) − (введённые расходы в `d`). Т.е. доход от
  работы входит **ступенями в дни выплаты**, а не равномерно.
- Без расписания — текущее поведение (равномерный дневной earned).
- Привязка к чекпоинтам (распределение остатка) — без изменений (линия по-прежнему проходит точно
  через каждый фактический чекпоинт).

## 15. Разрешения

Не применимо.

## 16. Краевые случаи

- E1. День выплаты не задан (`null`) ⇒ `payout=accrual` (текущее поведение).
- E2. `payout < accrual` ⇒ выплата в следующем месяце (декабрь→январь — перенос года).
- E3. Несколько ждущих лотов одновременно — суммируются в `unpaidNow`/`pendingNow`, выплачиваются
  каждый в свою дату.
- E4. Лот с `payout > end` — остаётся в `unpaidAtEnd`, не зачисляется.
- E5. Нет accrual ≤ anchor (первая отсечка позже якоря) ⇒ open-пул = вся работа ≤ anchor, лотов нет.
- E6. Фактическая дата без близкого запланированного payout ⇒ standalone выплата (accrual=payout=факт).
- E7. `today > end` — `nextSalary` отсутствует (как сейчас).

## 17. Состояния пусто/ошибка

- Пустое расписание → блок выплат показывает ежедневное начисление; карточки «ждёт выплаты»/
  «ожидаемая» не показываются (как сейчас при `!useDelayed`).

## 18. Валидация

- День зп и день выплаты: целые 1–28 (клампить). Пустой день выплаты допустим (`null`).
- `payDays`/`payoutDays` всегда одинаковой длины после любых операций.

## 19. План тестирования

Тестовой инфраструктуры в репозитории нет — использовать ad-hoc проверки `core.js` в Node (как в
предыдущих фичах) + ручную проверку в браузере. Ключевые проверки ядра:

- T1. `effectivePayEvents`: accrual=1, payout=5 → пары (1-е → 5-е) каждый месяц; payout=3, accrual=28
  → 3-е следующего месяца.
- T2. `payoutStateAt` на дате между отсечкой и выплатой: `pending` содержит закрытый период,
  `openMoney` = работа после отсечки.
- T3. `forecastSavings`: деньги периода появляются в `run`/`mean` в дату **выплаты**, а не отсечки;
  работа после отсечки не входит в эту выплату; `payDayDates` = даты выплат.
- T4. `payout=null` ⇒ результаты совпадают с текущей моделью (регрессия).
- T5. `cashFlowFromCheckpoints`: «выплачено» в интервале = сумма периодов с payout в интервале.
- T6. `node --check` всех JS-файлов.

Ручная проверка в браузере: график прогноза (ступень зарплаты в день выплаты), блок «Зарплата и
невыплаченное» (новая карточка «ждёт выплаты», даты по выплате), карточка «Дни выплаты» (два поля,
добавление/удаление синхронно).

## 20. Миграция / выкатка

- Авто-миграция при загрузке состояния (см. §11). Существующие пользователи: `payoutDays` = null-ы ⇒
  поведение не меняется.
- Старые клиенты через gist: игнорируют `payoutDays`, деградируют к accrual-как-payday. Указать в
  отчёте.

## 21. Критерии приёмки реализации

- AC1. `payout=null`/пустой `payoutDays` ⇒ численная регрессия с текущей моделью (T4).
- AC2. День зп 1 / выплата 5: рост баланса от зп в прогнозе на 5-м; работа 2–5 — следующий период (T3).
- AC3. Прошлое (реконструкция, cash-flow) использует даты **выплат** для роста баланса (T5, ручная).
- AC4. Блок «Зарплата и невыплаченное»: даты по выплате; карточка «Начислено, ждёт выплаты» при
  наличии ждущего пула.
- AC5. UI: два поля на строку, синхронные add/del, валидация 1–28, пустой день выплаты допустим.

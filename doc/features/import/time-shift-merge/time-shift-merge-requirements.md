# Догрузка экспорта: распознавание перераспределённых часов — интервью требований

Статус: интервью (спецификация ещё не пишется — ждём команду «напиши спеку»).

## Контекст задачи

Пользователь иногда перераспределяет часы по старым датам в Clockify. Из-за этого
у записей меняется время (а иногда и длительность). При повторной **догрузке**
(`mergeEntries`) такие записи не распознаются как «те же» и добавляются дубликатами,
а старые версии остаются. Нужно при догрузке распознавать перераспределение и
заменять старую версию новой, с достаточной точностью, чтобы не удалять нужные записи.

### Подтверждено из кода

- Запись = `{date, start, project, description, hours, rate}`. Поля `end` нет; время
  суток хранится только в `start`.
- **Время суток нигде не используется в расчётах**: `dailyAgg`, `monthlyAgg`,
  `weekdayModel` агрегируют по `e.date` (день). Время участвует только в `entryKey`
  (дедуп) и сортировке `byStart`. → менять логику идентичности безопасно для аналитики.
- CSV-парсер **не читает** `End Date` / `End Time`, хотя Clockify их экспортирует.
- В локальном сторе могут быть записи, добавленные **вручную** в приложении
  ([app.js:148-155](../../../../js/app.js#L148-L155): `start = ...T00:00:00`, пустое описание) — их нельзя терять.
- Тестовой инфраструктуры в репозитории нет.

### Корень проблемы

`entryKey` включает полный `start` (дата + время суток). При изменении времени ключ
меняется → запись считается новой и добавляется дубликатом; старая остаётся.

## Вопросы и ответы

1. **Что меняется при перераспределении — только время суток или и сам день?**
   Ответ: **Только время суток**. День (дата) остаётся прежним. → идентичность якорится на дату.

2. **Меняется ли длительность (часы) записи?**
   Ответ: **Часы тоже могут меняться**.

3. **Какие поля определяют «ту же» запись?**
   Ответ: должно совпадать всё, кроме времени начала/окончания.

4. **Что делать с локальной записью в диапазоне дат экспорта, которой нет в экспорте?**
   Ответ: **не удалять, а предупредить количеством таких записей**.

5. **Как сопоставлять в пределах одного дня, если поменялись и время, и часы?**
   Ответ (уточнение правила): сопоставление по **«день + проект + описание + ставка +
   общая продолжительность ±2.5 ч»**.

## Подтверждённые решения

- Фича действует **только на догрузку** (`file-merge` / `mergeEntries`). Полная замена
  (`file-import`) не меняется.
- Сопоставление — **пер-запись, 1-к-1**. Локальная запись и запись из нового экспорта
  считаются «одной и той же» (с перераспределённым временем), если:
  - совпадают `date` (день), `project`, `description`, `rate`, **и**
  - совпадает время начала независимо от разницы часов; **или**
  - при разном времени начала `|hours_new − hours_old| ≤ 2.5` (допуск ±2.5 ч
    по длительности **отдельной записи**).
- Алгоритм в пределах группы `(date, project, description, rate)`:
  1. Снять **точные дубликаты** по полному ключу (`start, project, hours, rate, description`,
     включая время суток) — такие записи уже есть, не добавляются и не заменяются.
  2. Оставшиеся локальные и новые записи **сопоставить 1-к-1**. Сначала предпочитать
     записи с одинаковым временем начала независимо от `|Δhours|`, затем — наименьшую
     разницу часов (`|Δhours|`) в пределах ±2.5 ч, ближайшее время начала и стабильный
     порядок. Каждая старая и каждая новая участвует в паре максимум один раз.
  3. Для каждой пары — **замена**: локальная запись удаляется, добавляется новая (со своим
     временем начала из экспорта).
  4. Несопоставленные **новые** записи — **добавляются**.
  5. Несопоставленные **локальные** записи — **остаются** (не удаляются).
- **Несопоставленные локальные записи, чья дата попадает в диапазон дат экспорта**,
  **не удаляются**, но пользователь **предупреждается их количеством**.
- Итоговое сообщение (toast) сообщает: сколько добавлено, сколько заменено, сколько
  оставлено-но-отсутствует-в-экспорте.

## Дефолты

- **D1 (нет пары по часам).** Если время начала различается и у записи нет партнёра в
  пределах ±2.5 ч → новая запись просто добавляется, локальная остаётся (и, если в
  диапазоне экспорта, попадает в предупреждение). Это естественное следствие
  пер-записной модели 1-к-1.
- **D2 (диапазон дат экспорта).** Диапазон = `[min(date), max(date)]` по записям нового
  экспорта. В предупреждение попадает несопоставленная локальная запись, чья дата
  попадает в этот диапазон.
- **D3 (ставка).** Сравнение точное (как в `entryKey`); записи со ставкой 0 совпадают между собой.
- **D4 (проект/описание).** Точное строковое сравнение (как сейчас читает парсер, без
  доп. нормализации).
- **D5 (время / конец).** Время суток не используется в аналитике; при замене берётся
  время начала из нового экспорта. Конец записи (`end`) отдельно не хранится и не
  сравнивается — он определяется как начало + длительность, поэтому совпадение по
  `(date, project, description, rate)` + длительности ±2.5 ч уже покрывает «и начало, и
  конец». Колонки `End Date/End Time` из CSV читать не требуется.

## Решённые вопросы

- **U1 — решено.** «±2.5 ч» = допуск по длительности **отдельной записи** (не по сумме
  группы) только при разном времени начала; при одинаковом времени разница часов не
  ограничена.
- **U2 — решено (дефолт принят).** См. D1.
